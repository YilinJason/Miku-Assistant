# 本轮交付顺序与验收依据

用户要求：除真实长测以外完成回收验收、等待优化；随后适当精简代码；最后优化等待、低配适应与资源泄漏风险。Codex 设计及每次严格评审、官方 Cursor CLI 实施；每切片通过再进入下一块。用户最新覆盖：忽略周额度阈值，仅短周期 Codex 窗口剩 <=10% 停止自有 CLI/测试并记录恢复，不自动消费 reset credits。

1. **资源回收**：当前 active 单次 owned-run 最终返修；随后持久 convert IO lease、未发布候选生命周期。里程碑检查进程/线程/文件/加载取消互斥、部分失败真实状态、重试有界，不以 daemon 或启动进程退出算完成。
2. **等待优化**：三模型预热接入 App 所有权、可取消与资源串行协调；有界一段 lookahead，可控低配串行模式；长句与过期音频清理。必须有冷/热阶段耗时、取消与资源上限证据，不盲增并行或超时。
3. **精简**：先建立通过基线，再按已测量的重复逻辑合并与单职责提取；纯结构变更与行为修复分开。保留旧入口/异常/预算/资源边界，不按行数删保护逻辑。不动无关记忆/安全/声学设置。
4. **性能**：依据基线控制线程/队列/捕获/文件/会话上限，低配有明确不加载重模型或串行降级路径，硬件未知不冒险预热。有限 fake 循环、短真实固定文本诊断（有总监督和资源采样）验证；不进行30–60分钟真实长测，不承诺绝对无泄漏或所有硬件低延迟。

Root静态确认待处理性能项：Edge `_speak_pipeline` 当前 `Queue()` 无界且正常join可等待600秒；producer可提前合成很多段，registry直到整轮结束才清。后续性能切片应与Cosy有界预取复用合适窄helper：最多1个future段（preparing或queued共1）、当前播放完成即清，取消不留producer/文件。此项属于行为优化，不能包装为纯结构精简；仍需现有late-output清理行为覆盖。
