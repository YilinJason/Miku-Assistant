# 语音运行时真机验收

本检查用于复验响应延迟、回复期间持续监听的防误触发/插话行为，以及异常退出后的资源回收。它会使用真实麦克风、扬声器、Ollama、edge-tts 与 RVC，必须由用户在设备前主动执行；离线测试不能替代本检查。

## 前置条件

1. 保存其他工作，打开任务管理器的“进程”和“性能 → GPU”页面。
2. 确认 Ollama 已运行，麦克风与扬声器可用。不要同时运行第二个助手实例。
3. 在项目根目录执行：

   ```powershell
   C:\Users\uitra\AppData\Local\Programs\Python\Python312\python.exe -X utf8 main.py --mode voice
   ```

4. 首次启动留意 `RVC Worker 预热`、`Ollama 模型后台预热已启动` 和 `[Ollama计时] 预热`。若显式开启重采样预热，还会出现 `MP3→WAV 重采样预热`。为了分别测冷启动与热态，不要把首次结果和后续轮次混为一个数字。

## 场景 A：持续监听但不误触发

1. 听到开始监听提示后，说：“你好，请用三句话介绍你自己。”
2. 记录终端出现首段文字的大致等待时间，以及听到第一段声音的大致等待时间。日志同时记录 `load_ms`、`prompt_ms`、`eval_ms`、token/s 和 TTS/RVC 分段耗时。
3. 助手朗读期间先保持安静，再制造普通环境声（键盘、风扇、远处谈话），不要说完整问题。
4. 查看 `logs/miku.log`：播报期间应继续出现“正在监听麦克风”，但不应出现新的有效“您说”或创建新回复；被门控的内容会记录 `[语音门控]` 原因，不记录正文。

通过条件：首段文字无需等待整篇生成完；回复期间持续监听；助手自身声音、语气音与普通环境声不会创建新回复。

## 场景 B：有效插话

1. 再问一个需要较长回答的问题。
2. 助手播报第一段时清楚地说：“等等，请只说结论。”
3. 观察旧声音是否停止、未播放句子是否取消，以及新问题是否只创建一轮回复。
4. 再试一次只说“停”，确认短控制词仍能通过门控。

通过条件：有效插话后旧回复在配置的有界等待内停止，不与新回复重叠；回声和语气词不会触发同样行为。

额外检查日志：若插话发生在 RVC 空闲时，应出现“RVC Worker 当前空闲”调试语义且下一轮不再记录 `RVC Worker 启动+模型加载`；插话正好撞上 RVC 推理时允许终止并按需重启。

## 场景 C：连续三轮与资源上限

连续提出三个短问题，每次等待播报结束再说下一句。观察任务管理器中的 Python、RVC Worker、CPU、内存和 GPU：

- 只应有一个主 Python 和至多一个常驻 RVC Worker，不应按句持续增加 Python 进程。
- CPU、内存和显存可在推理时上升，但每轮结束后不应持续阶梯式增长。
- 若 RVC Worker 超时或失败，本轮应改用普通 edge-tts 音色；不应逐句启动一次性 RVC 进程。

## 场景 D：正常退出与异常退出

先说“退出”完成一次正常退出，确认 Python/RVC Worker 均消失。重新启动后，可在助手空闲或播报期间直接关闭其终端窗口来模拟主进程硬退出；等待约 3 秒，再确认 RVC Worker 不再存在。

不要用任务管理器结束 Ollama，也不要执行关机、重启或锁屏指令。

## 结果采集

复验后保留以下信息即可：

- 首段文字等待约多少秒；第一段声音等待约多少秒。
- 朗读期间是否保持监听，环境声/助手回声是否创建了错误回复。
- 有效插话到旧声音停止、新回复开始分别约多少秒。
- 三轮后 Python/RVC Worker 数量，CPU/内存/GPU 是否持续不回落。
- 正常退出和关闭终端后，RVC Worker 是否在约 3 秒内消失。
- 若仍卡顿，提供本次测试时间点；日志已有阶段耗时，无需复制对话正文。
- 同时说明该轮发生在应用刚启动后还是预热完成后；两类结果应分别比较。
