# ADR：持续监听、回声门控与用户插话

- **状态**：已采纳（第一阶段；真实设备待验收）
- **日期**：2026-09-26
- **取代范围**：`adr-voice-stream-turn-taking.md` 中“回复期间关闭 STT”的产品默认行为；串行模式仍作为兼容路径保留

## 问题

串行轮流说话能阻止助手声音进入下一轮，但用户必须等完整回复与播报结束后才能继续说话。目标体验更接近移动端实时语音对话：回复期间麦克风仍保持监听，环境声、助手自身播报和低信息语气词不创建新轮次，明确插话则停止旧回复并立即开始新轮。

## 决策

1. 生产配置默认开启 `assistant.duplex_listening`。`VoiceSession` 主线程始终持有 STT；生成与播报在一个可追踪的 `VoiceReplyTask` 中执行，避免多个线程同时打开麦克风。
2. 回复期间识别结果先经过 `VoiceInputGate`。门控规范化文本，过滤与当前助手输出高度重合的回声、重复语气音和极短文本；“停”“等等”等显式控制词始终允许通过。
3. 有效插话同时设置本轮生成取消事件、按轮次失效尚未播放的句子，并调用 `TTSEngine.interrupt()` 停止当前播放器及 RVC Worker。旧任务须在有界时间内结束，否则会话暂停，避免新旧生成和音频任务重叠。
4. 系统控制、搜索和 LLM 回复都在播报前把同一份展示文本提供给回声门控。失败、空结果和取消文本不作为用户输入。
5. `TTSEngine` 使用中断代际区分旧轮与新轮。中断前已排队但尚未取得串行锁的旧 `speak()` 不得清掉新中断信号；仍在退出的合成线程所用临时文件不并发删除。
6. 旧串行模式与 `safe_to_resume_listen` 契约保留，供未声明全双工配置的注入环境和兼容调用使用。

## 与 ChatGPT 实时语音概念的关系

设计参考了实时语音系统的两个公开概念：语音活动/话轮结束判断，以及用户说话时取消当前响应并停止未播放音频。本项目没有接入 OpenAI Realtime API，仍使用现有 SpeechRecognition、Ollama、edge-tts 和 RVC。

当前门控发生在 STT 已返回文字之后，因此不是声学回声消除（AEC），也不是基于音频或语义模型的 VAD。它能阻止常见播报回声、短噪声转写和语气词进入业务层，但无法保证扬声器外放或复杂环境噪声永远不会被转写为看似有效的句子。真实扬声器场景建议先使用耳机；后续若要接近移动端实时语音质量，应增加可替换的连续 PCM 输入适配器，在 STT 前提供 AEC、VAD/端点和置信度，再将结构化结果送入现有门控。

## 已知限制

- `speech_recognition` 的阻塞录音不能在任意时刻硬取消；当前用短监听窗口降低响应延迟。
- edge-tts 网络保存阶段没有可靠的即时取消 API；播放器与 RVC 可主动停止，旧回复仍受有界等待保护。
- 当前没有“已播放音频 ↔ 文字 token”的时间对齐。若模型已完成并提交历史、用户在播报中途打断，历史里仍可能保存完整助手回复，不能像实时音频协议那样截断到实际已播放位置。
- 回声判定使用当前已生成文本；真实 AEC、语义 VAD、唤醒词和自由插话的设备调参不在本阶段实现范围。

## 验证

纯离线 fake 覆盖：回复任务运行时继续识别、助手回声不触发新轮、重复语气音/极短内容被丢弃、有效插话启动新轮、系统/搜索文本在播报前成为回声参照、旧播报任务不能清除较新的中断。真实麦克风、扬声器、Ollama、edge-tts、RVC 和环境噪声仍按 `docs/manual-voice-runtime-check.md` 单独验收。
