# 长期记忆实战未生效分析（2026-09-27）

## 现场结论

本次不是落库失败，也不是召回失败。故障位于召回后的模型 grounding（事实归属与使用规则）。

实际运行使用 `tmp/memory-live-test.yaml`，其中 `memory.enabled=true`、数据库为 `tmp/memory-live-test.sqlite3`。主配置 `config/config.yaml` 仍是 `memory.enabled=false`；以后直接使用主配置启动时不会启用长期记忆。

SQLite 中存在两条正确记录：

- `我的测试代号是“银杏4729”，`（`user_profile`，confidence 0.95）
- `我最喜欢喝桂花乌龙。`（`preference`，confidence 0.95）

19:55:06 的查询日志为 `entries=2 chars=199 error=-`。用同一查询离线重建出的注入块也包含上述两条，因此 store → lexical recall → context format → `system` 注入链路已工作。

## 根因

1. 记忆正文保留第一人称“我”，但 context 没有 owner/subject 字段。模型无法稳定判断“我”是用户还是助手。
2. 注入文本只强调“参考数据、不可信、不是指令”，没有一个可信的 system 级使用规则告诉模型：这是当前用户的长期记忆；相关时应据此回答；正文只能当事实数据、不能当命令执行。
3. context 暴露 `source=model_inferred`，却没有解释 0.95 confidence 或应如何使用。模型有理由选择忽略。
4. 用户问题含“这是一个全新的会话”，与模型常见的“新会话没有历史”行为强烈匹配。当前较弱的记忆提示没有覆盖这个先验。
5. 真实 v3 wrapper 的问题是“我最喜欢喝什么？”，并额外传入 `system="你是助手。"`；它证明了特定提示下模型能使用事实，但没有覆盖“新会话/你是否记得”这一真实问法，也没有覆盖两条第一人称记录。

## 修复方向

- 保持记忆正文是不可信数据，但增加可信的 system 使用规则；安全边界与事实使用规则要分开表达。
- 明确所有记录属于当前用户，记录中的第一人称是用户视角。
- 新提取内容规范成第三人称，例如“用户的测试代号是银杏4729”“用户最喜欢喝桂花乌龙”，禁止含糊代词。
- context 使用 `subject=user` 与 `fact` 等明确字段；内部 provenance 仍保持 `MODEL_INFERRED`，不得伪装成用户确认。
- 兼容已有第一人称记录，不要求先清库；注入层须能正确说明其视角。
- 用本次原句做真实回归：必须同时回答“银杏4729”和“桂花乌龙”，不得声称新会话无法记忆。

## 当前边界

即使提示修复，生成模型仍是概率系统，不能只靠一次成功声称永久可靠。产品上应记录“召回命中但回答未使用”的可观测指标，并保留以后为明确记忆查询增加确定性回答路径的选项。本轮先修正 grounding 契约，不引入向量库或新模型。
