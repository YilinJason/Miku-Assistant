# 安静环境语音误触发：代码审计与优化建议

日期：2026-11-05。状态：只读代码审计完成；尚未实施修复或做真实麦克风复测。

用户确认：异常转写发生在安静、助手也没有说话时。因此先处理噪声误触发；回声漏洞独立记录，不将其认定为本次根因。

本次应用仓库 architecture-contracts、engineering-quality、collaboration-review 技能。保留已有大量未提交修改；未调用 Cursor、未启动设备/模型、未调整运行中配置、未读取记忆库、未提交或推送。以下源码位置是本次审计时的位置。

## 已确认的代码缺口

1. **音量门限下限只在校准时有效，后续没有持续约束。**
   `src/voice/stt.py:176–182` 开启 SpeechRecognition 动态门限；`826–855` 在首次 0.5 秒校准后，将门限限制到 `max(300, configured_threshold * 0.5)`。本机安装的 SpeechRecognition 在等待起句及录音过程中仍反复按实际能量更新门限，没有这个下限。故配置 4000、校准结果 2000 不表示长期监听始终保持至少 2000。安静期间门限可能继续下降，随后小幅噪声可能触发采集。当前日志没有逐次触发门限，不能从日志证明本次每个异常确由此造成。

2. **录音时间被当成人声的近似判断，没有真正的无语音拦截。**
   `src/voice/stt.py:551–572` 调用 `Recognizer.listen()`，随后只检查总录音是否短于 0.4 秒。总时长包含保留的非说话帧，不能证明有人在说话。SpeechRecognition 自身还有约 0.3 秒的音量持续性过滤，可减少短促点击，但仍不是人声分类。
   `scripts/paraformer_runtime_worker.py:42–86` 仅装载 ASR，将整段 PCM 交给 `model.generate()`，没有配套 VAD。`src/voice/stt.py:702–708` 将成功且非空的 ASR 文本返回为 SUCCESS，没有额外人声证据。存在“噪声触发采集 → ASR 给出非空文本 → 作为用户输入”的路径；未获得异常录音，不能断言此次原始信号内容。

3. **空闲门控对短语气词保留较宽松。**
   `src/voice/input_gate.py:99–109` 对空闲状态的短语气词允许通过；输出期间才使用更严格的 filler/回声规则。这有自然交流方面的原因，但噪声若被识别成“嗯”等内容，也可能在空闲时触发对话。不能用禁止所有短句的方法修复，否则会损害正常应答和停止指令。

4. **没有明确绑定输入设备，也没有用户身份校验。**
   `src/voice/stt.py:509` 使用 `sr.Microphone()`，走系统默认输入设备。默认设备是否为预期麦克风、是否存在混音/虚拟输入，本次尚未验证。当前没有本人声纹注册或验证，所以其他人/电视中的真实人声也可能被当作输入；这与本次安静环境问题不同。

5. **独立的双工回声时序漏洞。**
   `src/cli/voice_session.py:228–263` 在录音和 ASR 都返回以后，才按当前时间判断是否还在回复结束后的回声保护期，过期就不再传入回声参考。当前保护期默认 1 秒；STT 停顿判句末为 1.5 秒，之后还有 ASR 延迟。可能出现：播报尾部被录到，等待句末和识别后已超过保护期，自己的声音成为新输入。
   `RecognitionResult` 当前不携带采集区间；仅延长保护秒数不能从根本上修复这一判断，也可能误伤真实插话。当前按完整生成文字做相似度过滤，同样不能替代声学回声消除。

## 建议实施顺序

### A：先修复安静环境误触发

- 明确麦克风设备配置与诊断显示，保留默认设备兼容入口。设备不存在时给出明确错误，不悄悄改用其他输入；不在诊断时偷偷打开录音。
- 明确门限策略：校准期间提示保持安静，校准结果有限且有界。可选受控的固定门限，或实现真正带上下限的动态门限；不能只在 `listen()` 前补一次 clamp，因为依赖内部仍会调整。不要修改第三方安装目录，也不要盲目把所有用户的下限锁为 2000。
- 在 ASR 前加入本地人声活动检测（VAD）。低成本信号检查先排除全零、异常格式等无效片段；VAD 再判断是否包含足够的人声。判定同时参考有效人声时长、连续性和相对噪声水平，参数需要通过正常音量、轻声和短指令回放调校。RMS/音量或 ASR 输出非空本身不能作为人声证明。
- 优先评估现有 FunASR 环境的 FSMN-VAD，以减少额外运行时；也可比较更轻的本地帧级 VAD。尚未做本机资源与误判对比，不宣布型号已选定。现有已验证版本是 FunASR 1.4.22，不因网站 main 分支示例而升级依赖。
- 无人声结果返回清晰的忽略原因，不能进入 LLM、历史提交、记忆提取或工具路由。短语气词与停止指令仍经过声学检查，但保留正常短句能力。
- 增加有界、可限频的诊断指标：实际输入设备、触发门限、录音/有效人声时长、拒绝原因和阶段耗时。默认不落盘原始录音、全文转写或声纹。

### B：随后修复双工回声边界

- 用单调时钟标记实际采集帧区间和实际播放区间，让结果返回再晚也不会丢失采集时的输出状态。仅在 `listen()` 调用前记时间会包含等待起句，不能等同于实际发声开始。
- 回声参考按实际播放过的段落、turn_id 和时间保留在有界结构中；不要把尚未播放的全部生成文字作为声音来源证据。避免错误地过滤用户复述助手的话。
- 补覆盖：播放尾部采集、句末等待、ASR 延迟超过保护期、取消后迟到结果、没有实际播放的生成内容，以及助手自己说出“停止”的情况。
- 软件文字门控无法保证扬声器全双工可靠隔离；耳机、串行监听可作为可选使用模式。未来如接入声学 AEC，必须接入真实播放参考并测量延迟，不能把延长计时器称为 AEC。

### C：若还需要“只接受我本人”

这是额外的交互与身份边界需求。VAD 只能判断是否有人声，不能识别本人。先提供近讲麦克风、按键说话或明确激活的交互入口；仅配置 wake_word 字符串不代表已有唤醒服务。声纹验证须另行设计用户主动注册、样本删除、误拒绝及录音重放风险，不能作为敏感系统操作的授权依据。不在本次噪声修复中自动采集声纹或引入额外大型模型。

## 资源、兼容与测试约束

- Codex 设计/审查；若进入实施，由官方 Cursor Agent CLI 编写代码和测试，完成每一阶段闭环后再进入下一阶段。遵守仓库安全策略和既有解释器边界，不改 RVC/Nahida 音色、不打开云 STT。
- VAD 模型如采用：仅语音模式按需初始化一次，固定本地资产和校验，下载走明确的既有准备流程；不在识别时隐式联网。尽量复用现有 ASR worker，保持现有 CPU 线程预算、单请求、有界 PCM、超时/取消及退出回收契约；不为每次录音新增进程或后台线程。
- 本次只分析现有测试，没有运行设备测试。现有 `tests/test_voice_input_gate.py` 覆盖文字相似回声和有效插话，不代表已覆盖本次声学误触发或迟到结果窗口。
- 实施后先用 fake 时钟、录音源、模型和播放端验证：安静长监听门限不失控；无语音不调用 ASR/LLM/记忆/工具；正常轻声、短句和停止指令可用；迟到结果门控正确；异常、取消、VAD 初始化失败及退出均有明确终态；缓冲和模型实例不增长。不默认启动真实设备或清理任务。
- 再做固定离线样本对比：静音、低幅稳定噪声、风扇/键盘/呼吸、正常与轻声短句、近似音量的非人声、外部真实人声、助手尾句回声。分别统计误接受与误拒绝，不能只验证 ASR 给出非空文本。
- 真实复测安排在用户结束当前运行以后，先做安静不说话 3–5 分钟，再做正常/轻声短句与播报尾部插话。记录本机 CPU/RSS/提交量、拒绝率、端到端延迟和退出后 worker/I/O 是否回收；给出样本与环境范围，不能承诺任意环境零误触发。
