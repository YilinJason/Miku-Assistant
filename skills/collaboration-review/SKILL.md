# 协作与评审

## 共同依据

读取根目录 AGENTS.md、当前任务说明、相关接口文档和 `git status`。以仓库实际文件为依据，不假定另一工具能看到聊天历史、未保存编辑或已加载同一组 Skills。
用户确认的顺序为工程化、实时对话、自然陪伴与长期记忆，再逐步扩展表现层；具体新指令优先，不自行扩大本次任务。

## 任务交接

为需要交给 Cursor 或其他开发者的任务提供以下内容；小任务可以用一段话表达：

- 目标和可观察的完成条件。
- 起始代码状态：相关提交（若有）及未提交修改，不要求为交接强行提交。
- 修改范围与接口约束，列出须保留的入口、配置和安全边界。
- 建议读取的技能及文件路径，明确已确认事实与待验证假设。
- 验证命令或场景、外部依赖、已知限制。
- 需要返回的变更说明、验证结果及遗留事项。

只有用户授权了消息发送才操作外部工具发送交接；否则在仓库文档或当前回复中交付可复制的任务说明。技能不授权另起代理、任务或后台协调。

## 工作区协作

- 避免双方同时修改同一文件；遇到实际重叠先阅读新变化并明确归属，再决定合并方式。不擅自撤销未知修改。
- 独立任务可划分模块，但跨模块协议须先统一。不要仅为形式上的并行拆出强依赖任务。
- 有必要隔离时使用合适分支或工作区，保留现有未提交内容。提交、推送、发布按用户当前授权处理，不由技能扩大授权。

## 评审流程

1. 阅读最终差异及其调用方，不只看实现者的摘要。
2. 优先检查行为回归、取消和关闭、错误语义、配置兼容、隐私及 SafetyPolicy 边界；格式偏好不应冒充功能缺陷。
3. 每个问题给出具体位置、触发条件、后果及可行修复方向。区分已确认问题与需实测的风险。
4. 检查验证证据是否覆盖改动；不得将另一工具声称“通过”直接当作自己已验证。
5. 对无关重构、提前选定 3D/XR 技术、绕过权限或新增大型框架提出范围审查，结合需求判断而非一律禁止。

## 完成记录

说明改了什么、为什么、验证情况及剩余风险。文档只更新受影响的内容，不复制整段聊天作为规范。
若需要维护跨轮任务记录，放在 `docs/` 中具名文件，使用清晰状态，并只在实际任务需要时创建。无法访问 Cursor 时如实说明，不声称已经与其通信或同步。
